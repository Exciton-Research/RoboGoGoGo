# RG Mobile Duo simulation

The supported simulation is the robot generated by
`robot/mobile_design.py`, using `simulation/mobile.py` and `Session(mobile=True)`.
The CLI and Studio construct this same model; there is no product robot catalog.
The engine is native Python/JAX and does not call an external physics engine.

## Coordinates and dynamics

The 31 coordinates comprise a planar base (3), wheel steering/rotation (8), folding
torso (4), two seven-joint arms (14), and pan/tilt head (2). The planar base is
constrained to level ground: roll, pitch, suspension and rollover are absent.
Forward kinematics, mass matrices, inverse dynamics and joint integration use
shared articulated-body primitives. Illustrative inertias and motor limits must
be replaced with measured values before drawing physical conclusions.

The mobile step applies tire forces separately from actuator limits, with steering,
longitudinal/lateral slip and a friction bound. Drive leases expire in simulation
time. Static support checks and dynamic acceleration-based support monitoring
reject unsafe predictions; this is not a tipping dynamics model or hardware safety
controller. See [the mechanical and driving contract](mobile-robot-design.md).

## Planned motion

Only the arms and torso participate in configuration-space detours. The planner
freezes base, wheel and head coordinates, validates endpoints, tries a direct edge
and neutral retreat, then uses bounded seeded RRT-Connect. Capsule clearance uses
adaptive swept-edge checks; support margin is sampled along candidate edges.
Uncertifiable edges are rejected and planning failure preserves the current goal.

Execution uses synchronized quintic joint references and rechecks each segment
from actual state. All predicted integration substeps pass runtime collision and
support guards before committing state. Stop, pause, cancellation and watchdog
semantics for simulation are separate from the command execution test backend.

Recorded policy deltas keep direct-path semantics; the recorder cannot overwrite
an active planned trajectory. No environment-map collision planner, grasp payload,
or physical trajectory execution is integrated with this mobile dynamics path.

## Numerical components and validation

Low-level contact, grasp, deformation, perception and recovery primitives remain
available for integration work. Their tests use minimal mathematical fixtures in
`tests/fixtures`; those fixtures are not additional product embodiments. The mobile
robot's rendered fingers currently have no articulated contact actuation. Passing
a fixed-base contact regression does not establish mobile handover capability.

Use `tests/test_mobile_design.py`, `test_mobile_driving.py`,
`test_mobile_self_collision.py` and `test_mobile_planning.py` for the supported
mechanism. They check model topology, tire behavior, stability boundaries, collision
rejection, detour edges, trajectory ownership and execution. Tests enable JAX double
precision; validation on physical hardware remains outstanding.
